## Blocking decisions

Severity here describes missing decisions before implementing or claiming the stronger contract, rather than new reproduced vulnerabilities.

| Severity | Decision and recommended default | Required acceptance evidence |
| --- | --- | --- |
| High | **Legacy trust establishment.** Existing V1 rows contain wrappers but no trusted public verifier. Do not allow account-session-only first registration, missing-verifier repair or verifier reset. Inventory existing vaults read-only before choosing a migration. Prefer limiting the new guarantee to atomically enrolled new vaults until an explicitly owner-approved legacy policy exists. If legacy bootstrap uses fresh account authentication/manual recovery, document that weaker trust assumption and hijack race; neither proves continuity with historical root. | New versus legacy states have an explicit policy; concurrent bootstrap attempts cannot replace the winner's verifier; interruption is atomic; missing migrated metadata never selects the legacy path. A restored pre-migration backup requires explicit operator reconciliation rather than an asserted cryptographic downgrade detector. |
| High | **Pinned authorization state.** Specify immutable verifier identity, algorithm, canonical public-key encoding/fingerprint and signer-artifact identity. Atomically install them with new-vault wrappers and setup identity. Seal independent private signing material under a separately domain-separated root-derived key; bind owner, vault, protocol, algorithm and verifier/artifact identity in authenticated data. Validate private/public correspondence after opening. Ordinary replacement cannot update any of these fields. | Cross-owner/vault/key/artifact substitutions fail; partial installation rolls back; setup retries compare every immutable setup artifact, not only existing wrapper fields. Corrupt or missing signer material fails closed without generating a new verifier. |
| High | **Complete intent and encoding.** Freeze a versioned, domain-separated fixed-position encoding, exact field types and complete wrapper representation, including nullable KDF/credential fields, salt, IV and ciphertext. Bind authenticated owner, vault, pinned verifier identity, operation kind, expected revision and operation ID. Do not accept a verifier/algorithm supplied by the request as the trust anchor. | Known-answer bytes and signatures agree across selected browser/server runtimes. Each field substitution, noncanonical encoding, unknown field, wrong algorithm and oversize input is rejected before mutation. Library defaults are not the wire specification. |
| High | **Receipt retention and semantics.** The present `lastOperationId + same(wrapper)` retry check omits expected revision and cannot recognize older successes after later replacements. Prefer durable accepted-operation receipts keyed by vault and operation ID, storing canonical intent digest, committed resulting revision and sufficient result metadata. Define retention and behavior beyond retention explicitly. Compare intent digests rather than signature bytes: a different valid signature over identical intent need not be a different operation. | Same operation ID/different signed intent always fails, including after intervening replacements. Lost acknowledgment retries succeed without a second mutation. Retry of success A after success B reports A as previously applied and B as current; it never reinstalls A or tells the client A is still current. Expired receipt behavior cannot authorize a replay. |
| High | **Recovery and signer loss.** Recovery must independently open the unchanged root and protected signer without the lost primary credential. Restore includes verifier, artifact, authorization-state marker and receipts consistently. Existing recovery still opens retained notes even when replacement authorization is unavailable. |
| Medium | **Algorithm and freshness.** Select one reviewed interoperable signing suite, exact key/signature formats and strict size limits after supported-browser review. New authorization-required vaults must reject old replacement requests on every mutation path. Decide legacy replacement behavior explicitly; do not infer permission to disable today's endpoint from this review. | Old clients retain intended unlock/read/save compatibility but cannot mutate authorization-required primary wrappers. ## Safe transaction and client invariants

### Candidate format for independent review

The first verifier establishes trust for subsequent replacements. Atomic setup can identify the winning request, but it cannot tell whether the account owner personally initiated it. If protection against a stolen session extends to first enrollment, the design needs a separately reviewed enrollment condition such as fresh provider authentication. Include two competing first enrollments and the losing legitimate client's recovery experience in the review. Require the client to validate its own setup identity and artifacts before it says its recovery kit works for the installed vault.

For an existing V1 vault, a fresh assertion by a registered passkey establishes present control of that credential. Its stored registration and last verification time do not bind a proposed signing key to the original root. Passphrase-only vaults also need a recovery path. The V1 recovery kit contains a recovery secret and checksum. Opening the original recovery wrapper with it can recover the root locally, but the server has no pre-enrolled signing verifier against which to validate a replacement intent. Treat a missing verifier in a restored or partially migrated vault as an ambiguous state that requires reconciliation. Keep existing notes readable with the saved recovery material while that decision is pending. [Vault schema](../db/schema/note-vaults.ts) · [Passkey schema](../db/schema/note-passkeys.ts) · [Recovery kit encoding](../lib/notes/encryption/crypto.ts)

Use ECDSA P-256 with SHA-256 as the first candidate. Pin a 65-byte uncompressed public key (`04` hexadecimal, followed by two 32-byte coordinates) at new-vault enrollment. Define the verifier ID as unpadded base64url of SHA-256 over those exact 65 bytes. Accept a 64-byte signature containing the two unsigned, fixed-width 32-byte integers in order. The algorithm comes from the pinned protocol version. The server can use Node Web Crypto to verify the original message bytes. Node's classic verifier needs explicit `ieee-p1363` encoding for this representation. [W3C ECDSA operations](https://www.w3.org/TR/webcrypto/#ecdsa-operations) · [Node Web Crypto](https://nodejs.org/api/webcrypto.html) · [Node classic signature verification](https://nodejs.org/api/crypto.html#verifyverifyobject-signature-signatureencoding)

For discussion, encode the signed message with the repository's existing UTF-8 JSON array convention. The outer array in order is `["eton", 1, "authorize-primary-replacement", ownerId, vaultId, verifierId, expectedRevision, operationId, wrapper]`. The version is specific to signed authorization. Use the field order of `canonicalWrapper` in `lib/notes/encryption/crypto.ts` for the nested wrapper array, including its nullable fields, salt, IV and ciphertext. Parse strict input first and reconstruct the arrays without whitespace or optional omissions. IDs and binary strings use the existing validated canonical forms. Specify the relying-party ID spelling for passkey wrappers, including ASCII domain representation and an exact match to the registered binding, before freezing fixtures. The server must independently compare owner, vault and verifier against authenticated and persisted state. A local check that the new primary opens the original root precedes signing. The signature never serves as that local check.

Use the signed-message digest for retry identity after verifying the signature. Keep the exact submitted request on the client for retries. A previously accepted operation can report its committed revision even after a later change. The client must separately obtain the current revision before it tells the user which primary is active. Specify retention and reconciliation before implementing receipts. A restored database or copied old root still needs a separate recovery decision.

One testable way to confirm root continuity across backgrounding is to discard the original unlocked key, reopen the proposed wrapper using the newly confirmed credential, and use that recovered root to open the **previously pinned** signer artifact. Bind the artifact to its vault and verifier, validate that its private key corresponds to the pinned public key, then sign. The client must fetch or reconcile the authentic current artifact before that check. A missing or corrupt copy should leave the original primary and recovery wrapper usable and report that replacement could not be completed. Verify the same flow using a recovery credential when the original primary has been lost.

The [local compatibility probe](../scripts/note-encryption-signature-compatibility.mjs) generated disposable keys and exercised fresh signatures in both directions between Node 26.12.1 and Chromium 158.0.8127.18, Firefox 159.0 and desktop Windows WebKit 27.2. Each browser verified a Node signature, and Node verified each browser's signature. The Node verifier rejected the altered test message for every pair.

The [public test vectors](../scripts/fixtures/note-encryption-signed-intents.json) specify one passphrase and one passkey replacement using the proposed wire format. Each contains named fields, the exact UTF-8 message text, its SHA-256 digest, a public verifier and a fixed signature. `expectedRevision` is a canonical UUID string, as required by the current replacement schema. The passkey example binds the relying-party ID, credential ID and PRF salt in order. An independent PowerShell/.NET reconstruction from the named fields reproduced both messages and digests and verified both signatures using fixed-width ECDSA. Future reviewers can reproduce the browser/Node check locally with `node scripts/note-encryption-signature-compatibility.mjs`. The probe has no application or database connection. These examples cover wire encoding and signature verification. The dummy encrypted fields cannot demonstrate root continuity, server authorization, replay handling or recovery after migration. Those behaviors still need review and, following implementation approval, separate tests.

For a new replacement: authenticate account/origin/protocol; parse bounded strict input; serialize against the authoritative vault and its pinned authorization state; verify the signature over the complete canonical intent; consult accepted-operation receipt; require current revision for a genuinely new operation; apply any new-credential policy; atomically write wrapper, new revision and receipt. An exact committed retry bypasses **new-operation** freshness checks, including the current ten-minute passkey-enrollment window, but never account authorization or signed-intent validation. Put no mutation before these checks, and keep the verifier immutable. Define retry verification explicitly before any future verifier rotation; rotation is out of scope here.

Receipt retention is not mandatory unbounded history, but a last-operation-only design must admit that earlier success becomes indeterminate and must still prevent operation-ID reuse. It must not claim durable exact-retry recognition that it cannot supply. A receipt's historical result and the current vault are separate facts; returning current state alone is not evidence that the submitted operation committed.

Before signing, the supported client must confirm the new wrapper opens the **same** root that opened the pinned signer. A valid signature authorizes arbitrary wrapper bytes; it does not prove root equality or decryptability to the server. Existing confirmation opens the candidate wrapper but does not compare the reopened root with the original raw root; today same-root preparation supplies that link. Specify a preserved local commitment/equality check across retained replacement intents and reloads, rather than relying only on an in-memory preparation assumption. Retain exact canonical intent/signature before sending; never silently re-sign changed revision or wrapper bytes after uncertainty. Lock/account-switch/epoch fences must also cover asynchronous signer loading and signing, and private signing material must not enter persistent plaintext storage.

The server's trust anchor protects against the stated account-session attacker only while that attacker cannot replace its persisted authorization state. A database writer/malicious server, compromised same-origin endpoint, or holder of the old root is outside this containment. Signatures and CAS provide no whole-state rollback resistance. A previously copied wrapper plus its old secret still reveals the unchanged root. Root rotation and authorization-key rotation need separate reviewed migrations; neither is an implicit credential-change benefit.

## Minimum release evidence after design resolution

1. Reject session-only replacement with both flags closed; reject wrong owner/vault/verifier, altered wrapper and reused operation ID with different intent, without any persisted mutation.
2. Accept primary-authorized and recovery-authorized replacements; retain exact recovery bytes and decrypt previously saved notes and sealed local work. Reject signed stale revisions and concurrent losing writers.
3. Exercise commit/lost acknowledgment/reload/retry, passkey policy expiry after commit, and retry A after later B; show no extra revision advance and truthful historical/current results.
4. Exercise interrupted new setup and selected legacy bootstrap, absent/corrupt/substituted signer state, old-client PATCH, backup restoration and protocol downgrade fences. Preserve recoverable work and require explicit recovery for indeterminate migration state.
5. Freeze reviewed protocol fixtures and exact source manifest; obtain independent protocol/security review and resolve all existing physical-device, accessibility/usability, production/operator and release-owner gates in the ledger.

The owner subsequently authorized implementation for new vaults while retaining the independent specialist gate. The current release scope records that implementation; this design record and primitive probes do not close that gate. Rollout flags remain disabled by default.
