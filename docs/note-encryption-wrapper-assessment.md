# Primary-wrapper authorization assessment

**Current implementation (November 18).** Local source commit `b8a6e54e90821433c9f26023b37a147aead22b6b` implements root-protected signed replacement for atomically enrolled authorization-version-1 vaults. Legacy version-0 vaults retain unlock and recovery without replacement. The assessment below describes the earlier vulnerability and proposed remedy. Independent specialist review remains open. [Current scope and evidence](note-encryption-release-readiness.md#current-pr-scope)

Assessment date: 2026-11-16. Reviewed local baseline `209ae968c720f63bcc5075ee43782bcb6ff0557a` on `feature/note-e2ee`. This is an engineering assessment and proposed remedy, not independent protocol approval or permission to enable either feature flag. No protocol, schema, UI, flag or production data was changed for this assessment.

The current November 16 release manifest records build `TW1Axqn5MoWv9bjgLTFW7`, source digest `13f804b6564b9b2029c5c4d081ce546a1c290f69d165beeb735c81b0165c4269`, and 89 source entries. Its historical comparison baseline differs from this assessment's starting commit. The release ledger already calls out account-session authorization for wrapper replacement as an open independent-review question.

## Finding

The server permits an authenticated account session to replace the primary wrapper without proving access to the existing vault root. The supported client unwraps the existing root first, but an attacker can call the API directly. This is a primary-unlock availability vulnerability under the narrower threat model of a stolen account session without access to the browser endpoint or vault secrets. It does not itself reveal the original root or original encrypted notes.

Evidence:

- `app/api/note-vault/route.ts:25` dispatches PATCH to `replacePrimary`.
- `lib/notes/encryption/server-http.ts:15` checks request origin, authenticated account and protocol header; these are meaningful cross-origin/old-client fences, not root-possession proof. A stolen session usable by a direct client can send the expected headers.
- `db/repositories/note-encryption.ts:27` accepts only operation ID, expected revision and new wrapper. `verifiedPrimary` at line 85 immediately accepts non-passkey wrappers at line 90. A replacement passphrase wrapper needs no current passphrase or recovery key. New-passkey verification at lines 91–106 proves control of the proposed credential, not continuity with the old root.
- `db/repositories/note-encryption.ts:153` checks owner, purpose, vault identity, exact retry and CAS. The update at lines 180–190 changes only primary wrapper, revision and last operation ID. Enrollment being disabled does not disable this path.
- `components/note/encryption/vault-controls.tsx:271` prepares a replacement by calling `rawUnlock` at line 286 and wrapping those bytes. Confirmation at lines 322–358 proves the replacement opens locally, but submits no old-root authorization.

## Attacker capabilities and limits

Assume the attacker has a valid account session only, can make authenticated requests, and does not have the current passphrase, PRF result, recovery key, root, or script execution in the victim's browser.

| Action | Consequence |
| --- | --- |
| Read vault and encrypted note APIs | Receives wrapped root, ciphertext and exposed metadata. The passphrase wrapper permits offline guesses against weak user-selected passphrases; generated phrases are a separate strength assumption. |
| Replace primary with schema-valid random ciphertext | Existing primary no longer opens the server's current wrapper. AES-GCM failure is detected by the client. No old-root disclosure follows. |
| Replace primary with an attacker-chosen root under an attacker credential | Attacker can open their replacement, but cannot decrypt existing notes or sealed local recovery records under the original root. New writes made by a client that accepts that substituted root could use the attacker's root. This requires a victim to unlock the substituted wrapper, for example after being persuaded to enter an attacker-provided passphrase; the original secret normally fails, so replacement alone does not silently grant future plaintext. This is a prospective confidentiality concern, not decryption of historical ciphertext. The current runtime retains an already-active root (`runtime.ts:50`), so replacement does not instantly change that tab's active key. |
| Repeat replacements after owner recovery | Can keep racing/disrupting primary repair while the account session remains usable. CAS is concurrency control, not authorization against the owner-equivalent session. |
| Modify encrypted note payloads through authenticated saves | Can submit schema-valid but cryptographically invalid envelopes, with current revision, or replace content with attacker-created encrypted content. Server validates structure and owner/mode/revision, not AEAD authenticity (`note-encryption.ts:241–309`). Recovery wrapper persistence cannot restore overwritten server note content by itself. |
| Trash or permanently delete notes | Existing account-authorized note lifecycle remains an availability boundary. Wrapper authorization alone cannot prevent it. Account deletion has an additional fresh-verification requirement (`app/api/user/account/route.ts:13–19`); do not claim any arbitrary stolen session can delete the account. A recently verified stolen session has a different risk. |

An account-session attacker is different from same-origin malicious JavaScript or an unlocked-device attacker. Endpoint compromise can observe inputs/decrypted content or invoke the active non-extractable key. The plan explicitly excludes that broader endpoint threat. A server database writer can also replace verifier material or delete ciphertext; a client signature requirement does not make a malicious server trusted or establish rollback resistance.

## Recovery continuity

The recovery wrapper is mandatory at setup (`note-encryption.ts:22–26`, `114–120`) and stored independently (`db/schema/note-vaults.ts:26–27`). Primary replacement does not modify it. No recovery-wrapper replacement/reset API exists in the inspected vault route. The saved recovery secret therefore continues to open the original root after an unauthorized primary replacement, assuming the original recovery wrapper remains available and the ciphertext has not been lost or overwritten.

`vault-controls.tsx:240–255` chooses the recovery wrapper independently, and replacement preparation uses the same `rawUnlock` function. Thus the supported UI can repair primary unlock using the saved recovery key even when the primary wrapper is junk. Repair is not durable containment until unauthorized account access is removed. A recovery kit is a secret, not a self-contained note backup: it also needs the wrapped-root material, server data or local sealed work, matching owner/vault identity and a compatible client. No export feature should be implied.

Both primary and recovery unwrap the same raw 32-byte root (`crypto.ts:253–299`; `candidate.ts:53–110`). Existing note fields and local recovery records derive their keys from that root (`crypto.ts:26–41`, `85–110`, `191–208`). Keeping the same root and recovery wrapper preserves their compatibility. A primary credential change does not revoke a previously copied primary wrapper plus its old secret, because that copy still reveals the unchanged root offline.

## Root compromise is separate

A copied root decrypts all captured ciphertext derived from that root, including note and browser recovery envelopes when available. It can also decrypt future ciphertext produced under the same root. Changing primary passphrase/passkey, signing out, locking a tab, or changing the recovery wrapper would not revoke the copied root. Current primary replacement deliberately rewraps the same root. Current code has no complete root-rotation migration.

A future compromise response needs a fresh independent root, fresh primary and recovery wrappers and a newly confirmed recovery kit; re-encryption of retained server notes; explicit treatment of offline drafts, in-flight immutable requests, conflicts, old backups, multiple devices, exact retries and interrupted migrations; and server/client epoch fencing. An old root cannot decrypt newly re-encrypted content if correctly migrated, but captured historical ciphertext remains exposed forever. Destroying old keys cannot erase an attacker's copies. Rotation must not silently orphan unsynced local work or claim retroactive secrecy.

## Options and compatibility

| Option | Benefit | Limit / compatibility / recovery impact |
| --- | --- | --- |
| Document and accept current behavior | No migration; saved recovery continues working. | Explicitly accepts session-only primary lockout and prospective substituted-root risk. Requires owner acceptance and independent review; not a technical fix. |
| Disable primary replacement server-side temporarily | Smallest fail-closed containment for this particular API. Existing encrypted read/save/unlock and recovery unlock can remain unchanged. | Changes the promised first-beta credential-change behavior. A lost primary can still unlock using recovery but cannot enroll its replacement until fixed. UI must truthfully explain the limitation. Does not stop ciphertext destruction by an account session. Requires product approval. |
| Require fresh account-provider authentication | Reuses account step-up concepts, no ciphertext migration. Reduces risk from an older stolen session. | Proves account-provider control, not vault-root possession; insufficient if the intended contract requires root authorization. Recovery should remain usable independently of a lost primary, subject to account login. |
| Require assertion from current primary passkey | Stronger for passkey-only replacement. | Breaks lost-passkey recovery and passphrase vaults unless additional authorized paths exist. New-passkey verification alone is insufficient. PRF is client-local and must not be sent to the server. |
| Server-verifiable vault authorization signature | An immutable public verifier at setup can require a vault-protected private authorization key to sign a canonical replacement intent. Passphrase, PRF and recovery can all unlock the same root/key. No plaintext or root needs to go to server. | New reviewed protocol/schema/client artifacts; existing-vault bootstrap needs an explicit trust decision. A signature authorizes replacement but does not prove the submitted wrapper actually encrypts the same root. Supported-client confirmation still matters. Root compromise also compromises authorization. |
| Send old root, recovery secret, PRF output, or wrapping key to server | None acceptable within this E2EE contract. | Violates the secret boundary and creates a server-side decryption capability. Reject. |

Proposed durable direction: design a separately scoped, independently reviewed vault authorization key whose private key is protected by the existing root, with only its public verifier persisted server-side and immutable after setup except through an already-authorized rotation protocol. Sign a domain-separated canonical intent binding owner, vault, expected vault revision, operation ID, protocol version, verifier identity and complete replacement wrapper. Verify before mutation; preserve exact signed retries and CAS. The verifier and protected private-key envelope need authenticated binding, strict formats/limits, fixtures and substitution tests. This is a design proposal, not a claim that adding an arbitrary signature field is sufficient.

New vaults can register verifier material atomically with setup. Existing V1 vaults have no previously trusted root-bound verifier; a session-only first-registration endpoint would let an attacker install their own verifier and merely move the vulnerability. Bootstrap therefore cannot honestly promise root-possession enforcement from existing ciphertext alone. Choose an explicitly trusted step-up/owner recovery migration, maintain restricted legacy behavior, or limit the stronger contract to newly enrolled vaults. Do not automatically assume all current vaults are disposable: flags being false today does not prove no enrolled vaults exist.

Adding fields to strict V1 schemas or requiring new request fields will reject old clients. Use additive database migration and a deliberate protocol/capability fence; preserve legacy unlock/read/save and recovery material while requiring reload for replacement. Do not mutate existing envelopes or regenerate recovery secrets for an authorization-only migration. Test restore from pre-migration backups and interruption before/after verifier registration. Root rotation is a separate future project, not a side effect of wrapper authorization.

## Selected direction and protocol review checklist

The owner selected **design vault-secret authorization; keep release blocked and current behavior unchanged pending review**. This resolves the direction of the first two decisions: fresh account authentication alone is not the target authorization contract, and no temporary disabling or production protocol change is authorized by this assessment. The following is a concrete review agenda, not a frozen wire format or implementation approval.

1. **Trust establishment.** For new vaults, atomically bind owner/vault/setup identity, immutable public verifier, signer-artifact identity and protected private signing material alongside the existing wrappers. Require client round-trip confirmation before activation. Inventory legacy V1 vaults read-only. Decide how a trusted step-up/manual migration establishes their first verifier; session-only trust on first use remains vulnerable to a hijack race and cannot prove continuity with their historical root. A fresh account-provider check is an explicitly weaker bootstrap trust assumption, not cryptographic proof of the old root.
2. **Signer protection and identity.** Select a reviewed signing algorithm and interoperable key format after browser/support review. Generate an independent signing key pair; seal the private material under a domain-separated root-derived key with fresh salt/IV. Authenticate owner, vault, protocol version, signer/verifier IDs, algorithm and public-key fingerprint in the signer envelope and validate that the decrypted private key corresponds to the pinned verifier. Do not reuse note/recovery AAD or include raw root, PRF output, passphrase or recovery secret in requests. Review whether strict envelope versioning or an independent signer-artifact version best preserves existing clients.
3. **Canonical signed intent.** Freeze a fixed-position array and canonical byte encoding with domain/version and explicit types. Bind operation kind, owner, vault, verifier identity/fingerprint, expected revision, operation ID and the complete canonical replacement wrapper (including ciphertext, IV and KDF/credential bindings). If hashing the wrapper, freeze hash and serialization rules; signing a wrapper ID alone is insufficient. Add cross-runtime known-answer fixtures, field substitution, malformed encoding, oversized signature and algorithm-confusion cases.
4. **Server transaction and retries.** Authenticate account/origin/protocol and validate bounded schemas. Load the pinned verifier and validate the signature over the complete intent before accepting any new mutation. Under existing account serialization, return success for an exact previously accepted signed operation with the same immutable intent; reject operation-ID reuse with different intent. Only then require current revision for a new operation and perform the CAS update. Define exactly what accepted operation digest/signature is retained so retries do not compare only a wrapper while ignoring other signed fields. Never make the verifier mutable through ordinary replacement, including retries. Test concurrent writers, signature failures, lost acknowledgments and older successful operations after later replacements.
5. **Freshness.** CAS binds authorization to the current vault revision and rejects stale new operations. Exact accepted retries are intentionally idempotent. Decide whether an expiring server challenge is additionally warranted and how expiration interacts with lost acknowledgments; do not casually add a challenge that makes an already-committed operation unreconcilable. Neither signatures nor CAS establish freshness against a malicious server replaying an entire old vault/verifier state. Preserve the explicit no-rollback-resistance claim.
6. **Recovery path.** Current primary or saved recovery secret must independently unwrap the same root, open the protected signer artifact, and authorize replacement. Do not require the lost primary credential as an additional condition for recovery. Verify the new wrapper locally before submission; signature verification establishes authority, not correctness of the wrapper's hidden root. Preserve exact original recovery-wrapper bytes and recovery-kit compatibility for an authorization-only migration. Test recovery after malicious/damaged primary replacement and missing/corrupt signer artifacts without destructive reset.
7. **Upgrade and restore.** Introduce additive storage plus an explicit replacement-protocol fence: an old client may still unlock/read/save/recover existing notes but cannot bypass authorization through the old PATCH shape. Specify how unsupported clients receive reload guidance without silently losing retained replacement intents. Test interrupted setup/bootstrap, restored pre-migration backups, unchanged note/local-recovery envelopes and restored signer artifacts. An absent verifier must not silently downgrade an already-migrated vault to session-only replacement.

Still open for reviewer/owner: the concrete signing algorithm and format; trusted legacy bootstrap policy and evidence; whether any independent account step-up should supplement vault proof; whether root-compromise rotation is required before beta or explicitly deferred with truthful non-revocation copy. A root holder can recover the signer and remains authorized; this design does not contain copied-root compromise.

These decisions are not authorization to deploy, enable flags, change production data or bypass the independent review gate.

## External corroboration

These sources were gathered by the task's separate documentation-research agent. They corroborate the rewrap/rotation distinction, not the proposed custom protocol: [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) distinguishes wrapping-key changes from data-key changes; [Bitwarden KDF changes](https://bitwarden.com/help/kdf-algorithms/) leave the symmetric vault key unchanged, while [account encryption-key rotation](https://bitwarden.com/help/account-encryption-key/) re-encrypts vault data. The server-verifiable authorization design above is an engineering proposal inferred from this repository's threat boundary and requires its own review.
