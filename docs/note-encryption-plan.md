# Opt-in note encryption: design and implementation plan

Status: design proposal, 2026-11-09.

## 1. Product contract

- Each note can be ordinary or encrypted. Existing notes remain ordinary until explicitly converted. New encrypted notes are encrypted before their first local or network persistence.
- Encrypt both title and rich-text body. Keep owner, note ID, vault ID, ciphertext size, timestamps, revision, trash deadline, archive state, and note color visible as operational metadata. Explain this disclosure.
- One unlock opens this account’s encrypted notes in the current tab. Keep Google sign-in separate. Prefer an app-enrolled passkey with verified WebAuthn PRF support for routine unlock. Allow synced and device-bound credentials. Offer a generated vault passphrase when PRF is unavailable. Users who choose a passkey need no passphrase.
- Each vault has one primary unlock method and a separate random recovery key. Before activation, prove both can independently reopen the same root. Ask users to save the recovery kit, then re-enter it with paste and explicit reveal available. Losing every usable primary credential and the recovery key means losing access. Explain that a device-bound credential stays on its authenticator and that access to a synced credential depends on its provider.
- The first beta supports notes created encrypted from their first save, editing, browser recovery, conflict review, trash/restore, passphrase change, and recovery-key unlock. A note keeps its creation mode throughout this beta. Both conversion directions are deferred. The conversion endpoints, journals, menu actions, benchmarks, and acceptance tests described below belong to the later conversion milestone. Encrypted draft recovery, exact retries, and conflict preservation are first-beta requirements.
- No sharing, collaboration, attachments, AI processing of encrypted content, persistent device unlock, or bulk encryption. Block remote images/embeds in encrypted notes while preserving literal ordinary links.
- Search excludes encrypted notes, including their titles, even while unlocked. Show a persistent explanation near search and a separate encrypted-note filter. Client-wide encrypted search is a later feature, not partial search presented as complete results.

## 2. Threat model and honest E2EE claim

The browser is the encryption endpoint. The server stores and transports ciphertext and wrapped keys, never a PRF output, vault passphrase, recovery secret, raw vault secret, title, or body for encrypted writes produced by the supported client. This protects new encrypted content in database dumps, infrastructure backups, and ordinary server read paths when that content has never existed there in plaintext. A backup taken after conversion may still contain old plaintext in WAL or physical page remnants.

It does not protect against compromised devices, extensions, XSS, malicious first-party JavaScript delivered by a compromised server, screenshots/clipboard, an unlocked session, denial of service, or all metadata analysis. A hosted browser client cannot independently defend against its code distributor. AEAD detects tampering but does not prove freshness against a malicious server replaying an old valid ciphertext/vault wrapper. No rollback-resistant security claim in V1.

Converting a previously ordinary note cannot erase old database backups, WAL, prior exports, other-device drafts, or physical storage remnants. Copy: "Encrypts future saved versions. Older copies may still exist in backups or on other devices." This limitation must be visible before conversion. Recovery-key possession plus access to wrapped-key material enables decryption; protect the recovery key like the passphrase.

## 3. Current repository constraints

- `db/schema/notes.ts` has `isEncrypted` and an `encrypted` theme value, but no cryptography. Never treat a flag or theme as encryption.
- `lib/notes/validation.ts` accepts title/content/theme only; snapshots, equality, reconciliation, and sync types assume plaintext fields.
- `lib/notes/drafts.ts` persists plaintext `baseline`, `draft`, `flight`, and `conflict` in Dexie, and exports the entire record as plaintext JSON. `session-sync.ts` also retains multiple versions and queued writes. Encrypt the complete sensitive record, not only its visible draft.
- `db/repositories/note-search.ts` excludes encrypted bodies but still indexes titles. Search SQL triggers protect only the body. Both must change before encrypted titles are supported.
- `db/repositories/account.ts` serializes interactive writes through a user row lock. Reuse that transaction boundary for vault and note transitions. Audit direct repository callers and Server Actions too.
- Notes use optimistic revisions, mutation IDs, and creation tombstones; preserve these semantics. Client creation IDs already become note IDs, providing a stable pre-encryption identity.
- `app/sw.ts` and `lib/notes/network-policy.ts` exclude protected note responses from caching and clean older caches. Extend coverage to vault endpoints and settings; do not depend on service-worker caching for offline recovery.
- `docs/archive/note-list-and-search.md` records an owner-required privacy-page update when encryption goes live. Current automatic server-encryption claims must be replaced with the actual opt-in client-encryption and ordinary-note storage contract as part of this release.

## 4. Key management and cryptographic format

Use browser Web Crypto, AES-256-GCM, a fresh random 96-bit IV for every new encryption operation, and a 128-bit authentication tag. IVs are never deterministically derived from revision/generation numbers. Use `crypto.getRandomValues`. Exact retries reuse the entire original envelope and mutation ID; never re-encrypt under a reused IV. Serialized ciphertext includes the authentication tag, with base64url encoding at JSON boundaries.

Generate one random 256-bit vault root secret. For each new note or recovery envelope, generate a fresh 32-byte derivation salt and use HKDF-SHA-256 to derive a non-extractable AES-256-GCM key, with the canonical AAD bytes below also used as HKDF `info`. Use each derived key for exactly one encryption; exact retries resend ciphertext. This avoids an unbounded aggregate GCM nonce budget under a single account AES key across devices and frequent draft seals. Independent random derivation contexts make key reuse negligibly likely without distributed counters. This adds no stored per-note key wrappers or distribution mechanism. Root compromise still exposes the whole vault. Future sharing needs a separate per-note-key/distribution review.

Store a note’s title and body in separately sealed envelopes committed together at one revision with one contentId. Give each envelope its own derivation salt, IV, and field-specific AAD. Validate the expected field and shared identity on read. This lets an unlocked list request only encrypted titles for its visible page.

For passkey setup, enroll a WebAuthn credential for the app’s relying party and require user verification. Use a fresh random PRF input per wrapper. Confirm support by obtaining an actual PRF result for the enrolled credential, including a fresh assertion before activating the vault. Derive a domain-separated AES wrapping key from that result using HKDF-SHA-256. Bind the credential ID, relying party ID, and PRF input to the wrapper. Freeze the exact encoding, derivation parameters, and fixtures during protocol review. Keep the result and derived key in browser memory. Explicitly exclude PRF output from serialized WebAuthn responses sent to the server, diagnostics, and persistence. Online enrollment must verify the challenge, origin, relying party ID and user verification on the server.

For the passphrase fallback, derive a wrapping key using native PBKDF2-HMAC-SHA-256, fresh 16-byte random salt, initially 600,000 iterations. Store a versioned KDF profile, never a passphrase verifier or hint. This is a portability/dependency tradeoff: Argon2id provides memory hardness, but requires a reviewed browser/WASM dependency. Benchmark native PBKDF2 on supported low-end mobile devices before accepting this choice; do not lower the iteration floor to meet a latency goal. Target unlock under two seconds on the agreed baseline device; revisit Argon2id before implementation if this gate fails. Do not represent OWASP's PBKDF2 password-storage guidance as a bespoke E2EE security endorsement.

Passphrase encoding is UTF-8 of the exact input, with no trimming, case folding, or Unicode normalization. Offer a strong generated multiword passphrase and allow password-manager paste; recommend generated phrases rather than suggesting a short minimum makes weak choices safe. Password quality policy is finalized in the crypto spike, including Unicode interoperability tests.

Wrap the raw vault root secret with AES-GCM under the selected primary wrapping key. Separately wrap the same root secret under a freshly generated 256-bit recovery secret imported as an AES-GCM key. Each wrapper has its own IV and purpose-specific AAD. The recovery wrapping key performs one encryption in V1; a future replacement must use a new recovery secret. Encode the recovery secret in a versioned, checksummed, copyable format. The checksum detects transcription mistakes; it is not authentication. Confirm recovery by successfully unwrapping the root with the re-entered recovery secret, not merely a checkbox.

At runtime import the unwrapped vault root as a non-extractable HKDF `CryptoKey`, with deriveKey usage only. Raw secret buffers exist briefly during setup/unwrapping and must be released promptly; JavaScript cannot guarantee memory zeroization. Runtime handles and secrets live in a private client module, outside persisted stores, query caches, logs, error reports, and URLs.

Canonical AAD is UTF-8 of a fixed-position JSON array, not arbitrary object serialization:

- Note field: `["eton",1,"note",ownerId,vaultId,noteId,contentId,field]`, where `field` is exactly `"title"` or `"body"`.
- Recovery: `["eton",1,"recovery",ownerId,vaultId,stableNoteOrCreationId,recordId,generation,capturedEpoch]`.
- Wrapper: `["eton",1,"vault-wrap",ownerId,vaultId,wrapperPurpose,wrapperId,profileIdOrNull,passkeyBindingOrNull]`. For passkeys the binding is the fixed tuple `[rpId,credentialIdBase64url,prfInputBase64url]`.

`contentId` is a client-generated UUID changed only for a newly encrypted logical payload; it is not the server-generated revision. The envelope includes derivation salt and all fields needed to rebuild AAD. Decoder accepts only supported versions/algorithms and canonical IDs/encodings, verifies salt/IV/tag sizes and bounds before crypto, then verifies the decrypted payload schema and existing HTML/size constraints. Never render ciphertext or failed decryption as HTML. Sanitize rich text before rendering even after authenticated decryption. AAD binds identities/purposes; it does not stop replay of a valid older envelope. The HKDF/AAD construction requires independent protocol review and interoperability fixtures in the crypto spike.

Authenticate recovery routing inside the sealed payload: stable note/creation identity, captured mode/epoch, source identity/epoch for a copy, flight destination, creation/mutation IDs, and expected revision. Strictly compare those fields with any clear outer routing copies before rendering, copying, restoring, or uploading. Specify fixed canonical types and explicit JSON nulls for absent fields. Captured epoch is immutable authenticated history; compare it with the live local marker separately. A stale marker comparison quarantines work for reconciliation rather than reporting damaged ciphertext. Test swapped outer routes, equal-generation cross-note substitution, and a copied record redirected to a different destination. Perfect replay of an old valid record remains outside the freshness guarantee.

## 5. Persistence and protocol contract

Store owner ID (unique FK), vault ID, format version, one typed primary wrapper (passkey or passphrase), a mandatory recovery wrapper, and a CAS revision in `note_vaults`. Store public credential verification and PRF parameters for the passkey variant, and KDF profile/salt for the passphrase variant. Delete vault and credential records during account deletion. No destructive vault reset in V1.

Add a dedicated versioned encrypted-payload field and vault reference to notes. Keep the existing flag, but derive validity through a database CHECK: ordinary implies no encrypted payload/vault; encrypted implies valid structural payload/vault and null plaintext title/content. Theme remains independent. Structural validity does not prove cryptographic validity to the server. Encrypted notes reference their owner's vault through an ownership-safe constraint/repository check.

API content is a strict discriminated union, `plain` or `encrypted`; reject mixed fields and unknown versions. Server never decrypts. Preserve original plaintext limits on the client; introduce explicit encrypted envelope bounds: up to 1,048,576 decoded payload bytes and 1,500,000 total request bytes, subject to a maximum-size multilingual HTML test and hosting limits before implementation. Bound streamed request reading before buffering, not only a `Content-Length` check. Bound wrapper KDF profiles before running expensive client work; clients accept a small explicit profile allowlist.

Owner identity always comes from authenticated server state. All mutating vault endpoints require same-origin protections, existing account serialization, strict schemas, and bounded input. Never put vault secrets or content in Server Actions, RSC props, SSR HTML, analytics, console output, or exception context. Sending wrapped keys and ciphertext to client components is permitted. Vault and encrypted recovery APIs return `private, no-store` and are NetworkOnly in the service worker.

Deploy a server-maintained minimum encryption-capable client protocol version before enabling conversion; an account becomes capability-gated once its vault is created. Reject unsupported mutation requests from headers before application body parsing where possible, and display reload-required in old supported shells. Current clients preflight remote mode/revision before replaying unresolved ordinary drafts. Version gates and row checks cannot prevent an old/offline client or already in-flight ordinary request from transmitting old plaintext bytes to the infrastructure, even if rejected. This is an explicit historical-copy limitation, not an E2EE guarantee. Audit edge/proxy/APM/request-body/error logging and disable content capture on note/vault paths. No promises about erasing traffic already sent before conversion.

Create/ordinary-save/encrypted-save/encrypt/decrypt are explicit operations with expected note revision. A save cannot change mode. Every legacy write path rejects plaintext content updates to an encrypted row; metadata-only trash/restore/delete remains possible while locked. Explicit conversion back to ordinary requires an unlocked client, clear confirmation that the server will receive plaintext, and revision CAS. After conversion, every save still checks mode/revision; stale encrypted writes cannot flip it back.

Retain creation tombstones and exact flight retries. An encrypted flight persists its exact envelope/mutation ID before upload. Server equality compares immutable envelope bytes for retries, not ciphertext equivalence to plaintext. Semantic equality and conflict merging happen in unlocked memory only. A conflict returns ciphertext plus metadata, never server-merged HTML. Resolve only after authenticated decryption of local/base/remote; preserve originals as encrypted recovery copies. Locking stops conflict resolution.

Primary-method replacement uses vault CAS and a stable operation ID. Freshly unlock with the existing method or recovery key, wrap the same root with the new method, prove it reopens independently, then commit. Keep the previous confirmed wrapper until the outcome is known. Refetch after an uncertain response or CAS loss. Recovery on a new device requires account sign-in and the saved recovery key, then allows enrolling a new passkey or choosing the generated passphrase fallback. Keep the recovery wrapper unchanged. Replacing an unlock method cannot revoke old copies of the root or wrappers. Root rotation and recovery-key replacement are deferred.

First-time vault setup is a unique-owner CAS/create operation with a stable setup ID. Candidate roots/wrappers/recovery kits are provisional until the exact winning tuple is confirmed by the server. An uncertain response requires refetch/retry before any encrypted note can be created. A losing setup tab discards its candidate root and recovery kit, fetches the winning vault, and asks the user to unlock it; it cannot cache or use its candidate as the account vault. Locally cached wrapper metadata must correspond to the confirmed winning vault identity.

Provisional setup handoff: retain only public candidate metadata, setup ID/submission status, and wrapped candidate root across backgrounding; clear PRF results, passphrase/recovery-secret fields, revealed kit, raw buffers, and derived keys. These sealed provisional records are distinct from a confirmed account vault and cannot authorize note encryption. Before switching to an external password manager, tell the user to save the kit first; after returning, resume setup through a fresh primary unlock and recovery-key entry, unwrap both candidate wrappers independently, and confirm their roots match before activation. This permits a single-phone flow without keeping revealed secrets or restarting every background transition. If the kit was not saved and its secret is gone, offer an explicit restart with a new candidate/kit only if no setup request was sent. Process termination before submission can likewise restart safely. Any submitted/uncertain setup must first reconcile the stable setup ID against the server; never replace a potentially committed winner. Recovery and passphrase-change forms follow the same background rule: keep only sealed intent/public stage and operation ID, clear secrets, re-enter to resume, and reconcile uncertain commits before issuing a replacement. Test actual app switching before/after kit saving and before/after submission, not only visibility events in automation.

Sequential verification makes two separate password-manager trips possible. At candidate creation compute a local domain-separated SHA-256 commitment to the uniformly random 32-byte root and the exact owner/vault/setup/wrapper tuple. Canonical commitment input is the UTF-8 fixed-position JSON context `["eton",1,"setup-root-check",ownerId,vaultId,setupId,primaryWrapperHash,recoveryWrapperHash]` followed by the fixed-length root bytes; wrapper hashes cover each canonical complete wrapper envelope. After a fresh passkey assertion or fresh passphrase entry, unwrap, recompute/compare, and record only a candidate-bound completed-check flag. Clear secrets on backgrounding. On a later trip, independently enter the recovery secret, unwrap, recompute/compare the same commitment, and record its completed flag. Activation requires both checks for the unchanged tuple, not simultaneously retained roots. A wrapper/candidate change invalidates both flags. This local commitment checks a random high-entropy root, is not an account credential, and must never authorize server activation or replace either wrapper/unlock operation; it adds no claimed password-guessing defense. Include its domain/encoding in protocol fixtures and independent review. Persist only this non-secret commitment, bound progress, and sealed candidate records between trips; no roots, derived keys, or secrets. Once the winning vault is confirmed, delete provisional progress and use the normal unlock flow if no root is currently available.

When replacing the primary method with a passphrase, freshly unwrap with the current method or recovery secret, generate a strong replacement phrase in-app, and seal its proposed wrapper while the root is still available. Let the user save the generated phrase externally; backgrounding clears all secrets. Resume by re-entering the saved new phrase and verifying its unwrapped root against an operation-bound local commitment computed at preparation. Bind that commitment/progress to owner/vault/expected vault revision/operation ID and the complete proposed wrapper hash; tuple changes invalidate it. Only then submit the wrapper CAS. An ambiguous commit must reconcile before retry/restart, and the old confirmed wrapper stays authoritative until commit is proven. The generated-phrase flow is the supported one-phone path; custom new phrases require both old/root access and new phrase within one foreground session and must not create a secret-retention exception. These checks do not revoke old data access or make local progress flags server credentials.

## 6. Conversion and local recovery state machine

Remote transition and local IndexedDB cannot be one transaction. Treat conversion as a recoverable journal, not a boolean toggle.

1. Online only: unlock, fetch current mode/revision, block new edits for this note, and settle outstanding flights. If acknowledgement is uncertain or a conflict exists, resolve first. If the note changes remotely, abort and retry against the latest state.
2. Acquire a per-account browser write lock briefly to read markers and capture matching record identities/generations, then release it. Check the conversion work limit below before staging. Every draft writer and conversion participant must use the same Web Lock for marker validation and atomic commit. Update the Dexie schema with a transition journal, encrypted record variant, and durable per-note mode/epoch table keyed by `[ownerId, noteId ?? creationId]`. Keep mode/epoch markers after journal completion. Every put, clear, retry, export, and newly created recovery/edited copy must re-read the marker under the lock and validate its captured epoch/mode. A stale writer cannot regain permission by changing record ID or having an equal generation. Abort conversion if required browser coordination/storage capabilities are missing. Notify other supported tabs to pause and clear this note's in-memory view. Never hold this lock during KDF, encryption/decryption, network, confirmation dialogs, or unbounded record scanning.
3. Snapshot all matching browser-work records by stable note identity (including null-noteId records whose creationId is the note ID, retained and edited copies). Outside the lock and Dexie transaction encrypt their complete sensitive subtrees and the new server payload. Reacquire the lock, atomically recheck captured generations/epochs and the matching-record set, increment the durable epoch, set transitional encrypted mode, replace matching records, and write the exact encrypted transition request/journal. Repeat preparation if a generation or record set changed; never do asynchronous crypto inside an open IndexedDB transaction. An async callback must recheck the epoch after reacquiring the lock. Clear old query/editor/session projections. Use a clear outer metadata record for IDs, ordering, and locked status only. Copies made into a new independent note inherit encrypted mode; making an ordinary copy requires the explicit decryption flow.
4. Send the recorded encrypt operation with expected remote revision. Server commits the mode change, ciphertext, null plaintext columns, revision advance, and removal of all title/body search projections in the same transaction.
5. On acknowledgement (or refetch proving the exact mutation/envelope committed), finish the journal, refresh collections, and announce success. If upload fails, retain encrypted local work and show "Encryption pending; server status unconfirmed." A fresh authoritative ordinary-mode read permits the more specific "The server copy is still ordinary." Do not mark it encrypted on the server prematurely. A crash at any boundary resumes from the journal after unlock; no plaintext fallback.

Journal recovery is deterministic and conservative: an exact current mutation/envelope match proves success. If the remote note is encrypted but its mutation has advanced, treat it as encrypted and preserve sealed local work for unlocked conflict review; do not overwrite or claim the precise prior operation was confirmed. If remote is ordinary at the unchanged expected revision, the original encrypt request may retry with its exact identity; if the revision changed, stop for review and never auto-convert that version. If the note is trashed, follow the existing deadline/state rules and keep local work sealed for review; if missing/expired/deleted, never recreate the original identity and retain a sealed recovery copy. If offline, remain pending. Metadata checks may resume while locked; decryption/review requires unlock. No permanent operation-receipt table is needed for V1.

Reverse conversion has its own journal and explicit warning. Persist only a sealed intent containing the plaintext content, expected revision, and stable operation ID; construct the ordinary request in memory after unlock. Never persist the plaintext outbound flight, even for exact retries. Reconstruct identical request fields from the sealed intent for a retry. Keep encrypted local copies and durable encrypted/transitional mode until an exact commit is acknowledged or proven; only then permit ordinary recovery persistence. If the remote is ordinary at a later revision, do not overwrite it or auto-unseal local records: keep the intent sealed for review. Remote still encrypted at the unchanged revision allows the original request to retry after unlock. All other outcomes follow the conservative recovery rules above. Never automatically retry a mode change using a newer revision.

Other devices may retain old plaintext recovery data. On reconnect, before displaying/resending a draft, check the remote mode/revision. Quarantine stale plaintext work for a newly encrypted note: never upload, preview, or export it through a generic action. Require unlock and encrypt it in place before review. A stale device's ordinary local copy cannot be remotely erased, including while offline. An old unsupported client may also retain plaintext locally; server write fencing is enforceable, local erasure is not. Deployment requires an updated-client handshake and reload guidance; do not claim protection for old offline clients or forensic disk recovery.

On a capable device receiving a remote mode/revision change, acquire the local write lock and atomically initialize/advance its durable marker and quarantine all matching ordinary records before generic list/preview/export processing resumes. Do not infer a safe plaintext mode from an absent marker. Independently created copies retain a source-note identity and captured source epoch until the copy operation commits; validating only their new destination ID is insufficient. Remote changes after preflight can still race with ordinary requests already in flight; include this documented historical-plaintext exception in the privacy audit rather than claiming zero ingress.

All encrypted draft persistence encrypts the complete record subtree, including baseline, flight, conflict, retained sources, and edited versions. Decrypted objects never enter Dexie, persistent Zustand state, service-worker caches, or generic export functions. Portable encrypted export and import are deferred together in V1; generic export must reject encrypted records and quarantined ordinary records rather than exposing them. Retain sealed work across sign-out through the existing keep-on-device flow, partitioned by owner. Explicitly confirmed discard/account deletion removes it. Storage eviction/device loss can still lose local-only work; show this limitation and distinguish local from synced. Ordinary drafts keep their current behavior. A future export must include a tested matching import path before offering downloads.

Offline policy: V1 supports local encrypted work only in an already-loaded application shell. Cold offline reload/navigation after browser or process termination is not supported because protected navigations are NetworkOnly. Keep private HTML/RSC/vault responses uncached; a future account-neutral offline recovery shell is separate work. Persist authenticated encrypted vault wrappers/KDF metadata and encrypted drafts locally, associated with the last confirmed owner and vault revision; never persist secrets. In the loaded shell, the user may unlock local records using the recovery key or an enrolled passphrase. Offer offline passkey unlock only for combinations verified to return the PRF locally in the loaded shell. These paths operate without claiming a live authenticated account session. Network operations and remote-mode reconciliation wait for authentication/connectivity. After reload or on a new device, opening recovery requires the app to load online and the user to authenticate before the authoritative vault is fetched. Retained local wrappers permit old primary credentials to unlock old local material after remote replacement; this follows the non-revocation contract. Explicit sign-out/account switch clears in-memory access. Local owner identity is a namespace, not proof of server authentication. Show the online-reopen requirement before offering keep-on-device.

## 7. Locking, editing, and UX

- Settings offer setup, unlock/lock, replace unlock method, and recover access. Show the device prompt first for a passkey vault. Cancellation leaves the vault locked and permits retry or recovery without changing the primary method. Explain loss, replacement, metadata, and backup copies.
- Note menu: Encrypt note; encrypted note menu: Make ordinary. Do not reuse note color as a security toggle. New-note flow offers an encrypted choice before editor creation/persistence.
- Locked cards show “Encrypted note”, a lock icon, ordinary metadata, and an Unlock action. Keep titles out of snippets, ARIA labels and document titles while locked. In the unlocked encrypted-note list, fetch title envelopes for the visible page in one bounded request and decrypt locally. Fetch the body only when opening a note. Clear displayed titles and invalidate pending requests on lock or account change. Keep decrypted titles out of server search and client search overlays.
- State machine: unconfigured -> locked -> unlocking -> unlocked -> locking -> locked, with wrong-secret, unsupported-browser, damaged-data, local-storage-failure, and sync-conflict paths. Wrong credentials and damaged wrapper may share a safe message, with a recovery option; no destructive automatic repair.
- Manual lock, sign-out, and account change invalidate all cooperating tabs. Backgrounding or 15 minutes of inactivity lock only the affected tab; opening a sibling tab must not lock the newly active tab. On backgrounding, immediately hide sensitive content and begin local sealing/key removal; returning requires unlock, including after using a password manager. Warn about this behavior during setup without asking to weaken it. Seal pending work continuously during editing; do not depend on `beforeunload` completing crypto. On lock, invalidate async callbacks with a session epoch, seal latest edits locally, then drop keys and clear editor/undo state, query-derived plaintext, counts, dialogs, and previews. Cross-tab events carry invalidation metadata, never keys. Recheck account/unlock epoch after every awaited crypto/network operation.
- If sealing fails, hide the editor and retain the minimum dirty content/key only in a blocked locking state with a clear save/discard choice; never claim "Locked" until it is sealed or explicitly discarded. Page/process termination can lose unsealed edits. Show saved/local/unsaved status accurately. Unsupported browsers can still use ordinary notes but cannot edit encrypted notes.
- No cross-tab automatic key sharing. Each tab unlocks independently; lock notifications apply to all cooperating tabs. On pageshow/BFCache and return from background, enforce locked UI before rendering content; suspended JavaScript cannot promise immediate physical memory clearing.
- Use existing dialogs/primitives/tokens and EN/VI translations. Keyboard focus and announcements must cover locking, recovery-key confirmation, errors, pending conversion, and blocked locking.

### Error recovery and status language

Keep encryption/access status separate from persistence status: "Locked" or "Unlocked"; "Encrypted on this device" versus "Encrypted and synced"; "Latest edits not saved"; and "Encryption pending; server status unconfirmed" after an ambiguous response. Only say the server copy is ordinary when a fresh authoritative read proves it. A lock icon must not imply sync completion. Announce transitions politely, reserve urgent alerts for actionable failures, and avoid announcing each keystroke/checkpoint.

Quota/storage failure offers retry and an explicit named discard; never delete the last readable checkpoint or unique retained copy automatically. Because portable export is deferred, plainly warn that closing the tab can lose unsaved work; do not offer a nonexistent download escape. A damaged individual note blocks only that note, preserves its ciphertext, and offers retry/refetch or recovery-copy review without overwriting local work. Wrong-secret retry must preserve entered non-secret state and allow recovery-key entry; account deletion must not be presented as a remedy for unlock failure. Irreversible discard requires a second confirmation naming the note or count and whether work exists only on this device. Setup/recovery/passphrase-change errors preserve the old confirmed vault; do not show provisional setup kits as active.

## 8. Performance and resource contract

These are proposed release budgets, not measured results. Use synthetic fixtures on a named low-end Android device (initial baseline: Samsung Galaxy A14 4 GB, current supported Chrome) and a desktop browser; record OS/browser/device versions, warm/cold conditions, fixture sizes, and p50/p95 over at least 30 runs. If that device is unavailable, select and document a comparably constrained physical device before accepting mobile results. Throttled desktop measurements are preliminary evidence only. Benchmark WebKit separately on a named supported iPhone before claiming iOS support. Never weaken sealing, authentication, or the KDF floor to pass a timing budget.

- Checkpoint scheduler: per open note, at most one active seal and one replaceable latest pending generation. Coalesce superseded routine local checkpoints; do not replace immutable flights, conversion intents, or unique retained/conflict work. Completed generation `g` may commit even while newer edits exist if its account/session/mode epochs and routing still match, it is newer than the durable generation, and it preserves the currently required immutable flight/intent. Validate these conditions under the lock; never overwrite a newer durable record, erase a new flight, or advance the durable checkpoint beyond `g`. Later edits stay pending and visibly unsaved until their own checkpoint commits. This permits monotonic durable progress during continuous typing rather than discarding every completed seal. An invalidated controller/epoch or incompatible flight change must discard its result. Across a tab, use one recovery-seal worker loop with round-robin fairness between notes; foreground and lock-finalization work take priority. Start with native async Web Crypto and cooperative yielding around serialization; add a dedicated worker only if main-thread profiling fails the budget. Serialize unlock attempts and deduplicate them per tab; use PBKDF2 only for passphrase unlock/rewrap.
- Preserve existing local scheduling intent (500 ms idle, 2 s maximum scheduling delay), measuring both stable-edit commit latency and the age of the latest durable checkpoint during sustained typing. For a normal note (up to 32 KiB UTF-8 title/body combined), healthy storage stable-edit local-commit p95 must be at most 2.5 s; target durable-checkpoint age p95 at most 2.5 s during continuous normal-load typing. A 30-second rapid-edit test with artificially delayed crypto must never exceed the finite queue or label a newer generation saved than actually committed; completed valid seals must make monotonic durable progress. Crash midway and verify recovery of the exact latest committed snapshot and every protected immutable flight/retained copy, with later unsaved edits explicitly within the loss window. Superseded coalesced intermediate checkpoints are not version history and need not be retained. Max-size content has its own published timing: target local-seal/commit p95 at most 5 s after a stable generation. Artificial delays beyond those budgets are failure-injection cases, not successful latency evidence. If saturated, show unsaved/saving, yield to input, and keep the newest work; no growing queue.
- Preserve server-save scheduling rather than uploading every checkpoint (currently 3 s idle / 30 s max and 10 s minimum attempt interval). Reuse a generation's prepared encrypted wire envelope; retries resend exact bytes. Loading 1,000 encrypted note/recovery headers must read/decrypt zero body payloads, perform zero KDFs, and make zero per-note detail fetches. Measure visible-page title decryption separately from the header scan. Fetch and decrypt zero bodies for the unlocked list. Only an explicitly opened note or requested recovery version loads its body. No all-record JSON-stringify comparison: group headers by opaque version/source IDs and revisions; do semantic deduplication only for selected unlocked versions.
- Separate IndexedDB header and sealed-payload tables with indexes for owner, stable note identity, updated time, status, and source/version IDs. Paginate headers (initial page at most 50), leaving payloads out of list/focus queries. Outer sizes/timestamps/counts are disclosed metadata, not content-derived hashes or plaintext snippets. Avoid hashing plaintext into clear deduplication keys. Refetch affected headers after changes rather than rescanning/decrypting every record.
- Network and local recovery budgets are distinct. The proposed wire cap remains 1 MiB decoded encrypted note payload / 1,500,000 request bytes. A local record can include baseline, draft, flight, and remote conflict, so provisionally permit 8 MiB decoded serialized recovery payload and 12 MiB encoded stored record, including bounded routing metadata. Define exact allowed record variants with no recursive embedded records; retained/edited copies are separate paginated records, never nested histories. The spike must enumerate worst-case Unicode/JSON/base64 expansion for every accepted variant and freeze compatible caps; adjust the provisional local cap upward if needed to preserve every already-supported valid note shape. Reject an oversized incoming/new operation before replacing previous work, with clear unsaved status; do not silently truncate content or evict unique copies to meet a budget.
- With 1,000 recovery headers and at least 20 largest-supported distinct retained records, header list/focus refresh p95 must be at most 250 ms on desktop and 500 ms on the mobile baseline once IndexedDB is open; body count remains zero. Selected normal-size detail decrypt/validate/sanitize p95 at most 150 ms, excluding KDF/network and existing editor mounting. Typing must introduce no encryption-attributable main-thread task above 50 ms. Track stored byte growth in a maximum-size conflict scenario, not only happy-path ciphertext size. Quota injection must leave the preceding committed checkpoint readable and the newest generation visibly unsaved.
- Treat a note's retained versions as separate bounded records and stream conversion preparation in small batches outside locks. Retention is not capped, but a single conversion operation is: at most 64 affected records and 32 MiB total staged encoded ciphertext, including the note payload and all retained work. Preflight with the indexed stable-note record count (stop after 65) and byte-size metadata; freeze note-local writes through a transition marker while staging. Enforce the byte limit on actual output as it is staged, and revalidate the bounded record set under the lock at commit. If either limit is exceeded, stop with "Too many retained versions to convert on this device. Review browser work before trying again." Keep every original and unique version; never auto-delete, partially convert, or suggest that ordinary content is encrypted. Users may deliberately review/sync/discard named copies under the existing safety confirmations, or leave the note ordinary. V1 does not promise conversion of an arbitrarily large retained history.
- For an accepted conversion, stage ciphertext payloads without replacing originals until the final atomic mode/epoch commit switches header references and removes old plaintext records; no crypto or full payload copying in that commit. If staging hits quota, abort safely and keep the source ordinary with recoverable work intact. The journal enumerates the bounded staged set, so partial conversion cannot be called complete. Target final conversion commit/lock p95 at most 250 ms on the named mobile baseline, measured at both the record-count and byte limits; lower the accepted operation limits or redesign the commit if profiling misses this target, never omit exact-set validation. Test 64 versus 65 records and staged bytes immediately below/above the cap. For 20 largest-supported retained records, an operation-limit refusal is an expected safe outcome, distinct from the separate per-record seal/reopen test. Clean abandoned staging by journal ownership only, preserving every committed source/checkpoint.
- Measure timings, queue depth, crypto invocation counts, payload-read counts, and byte totals using synthetic benchmark fixtures. Keep benchmark telemetry local. Production diagnostics, if added, contain only coarse duration buckets and outcome enums after privacy review: no note/owner identifiers, plaintext lengths, content, secret material, input events, or clipboard data. Never run an automatic decryption/upload benchmark against real user notes.

## 9. Acceptance criteria

| Dimension | Design criteria | Required implementation evidence |
| --- | --- | --- |

| Performance | Finite queues; short locks; lazy payload access; bounded record shapes; explicit latency/storage budgets; no content telemetry | Named-device benchmark report at normal/max sizes; 1,000-header zero-body-read test; 30-second saturated queue test; main-thread profiles; quota/retained-version conversion tests meeting section 8 |

Before beta, each acceptance row must have linked evidence for the first-beta scope and an owner for any remaining work. Exercise the setup, encrypted creation, unlock, and recovery tasks in the usability study. Conversion-specific evidence is due before enabling conversion. A missed timing target triggers profiling and design review; a security/safety failure blocks release. Before accepting real user notes, complete independent protocol review and demonstrate phone enrollment, encrypted creation, relock, repeat unlock, and fresh-device recovery of the same note without the original credential. Test missing PRF output, prompt cancellation, provider-induced backgrounding, a lost credential, and the generated-passphrase path. Record the tested browser, OS, and credential provider for each supported combination.

### Existing-feature release checks

Record baseline results on the pre-encryption revision using disposable accounts, databases, and browser profiles. Run the same checks on the release candidate. Record revisions, feature-flag settings, and actual results. A skipped suite or missing fixture leaves its check open. Fix and rerun any regression introduced by encryption before enabling or expanding the beta.

- Exercise the upgrade with ordinary notes, a trashed note, and an unsynced browser draft created by the previous version. With enrollment disabled, verify the upgraded client can open, edit, sync, and recover them. ## 10. Build sequence and exit criteria

1. Crypto/protocol spike: verify passkey PRF enrollment, repeat unlock and recovery on target devices before making it the default there. Finalize fallback passphrase policy, AAD/envelope fixtures, KDF allowlist and mobile timings, browser support, byte limits, recovery encoding. Verify known-answer/interoperability tests, wrong-secret and tamper failures, Unicode round trips, fresh IVs, purpose/owner/note/field/credential/routing substitution rejection, and unsupported version handling. Enumerate allowed local record shapes and benchmark section 8 budgets before freezing the storage protocol. Exit: documented supported browser/device matrix and reviewed protocol.
2. Server foundations with feature disabled: additive vault/payload schema and CHECK/FK constraints; explicit operations, CAS/idempotency and all legacy-path fences; search SQL triggers/backfill handling and account deletion cleanup. Audit pre-existing `isEncrypted=true` rows first: quarantine unsupported rows, never label plaintext as safely encrypted or auto-invent keys. Verify owner denial, malformed/oversized payload rejection, concurrent setup/rewrap including a losing candidate root and lost setup acknowledgement, stale mode writes, retry tombstones, no index residue, and rollback atomicity in an isolated database.
3. Browser storage and sync: versioned encrypted Dexie records, journal, write locks, durable mode/epoch fences, immutable encrypted flights, and quarantine. Verify crashes and quota failures at every conversion step; queued stale writers (including equal generations, new edited-copy IDs/source epochs, and null noteId); loaded-shell offline unlock/edit/reconnect and online reopening after termination; reconnect quarantine before generic rendering; lost acknowledgements followed by later edits/trash/delete; reverse conversions with no persisted plaintext intent; account switching; conflict preservation; and lock while crypto/upload is pending. Test generic export refusal and keep/discard-on-sign-out. Ordinary-note regressions must remain green.
4. Product UI: setup/recovery confirmation, per-note actions, locked detail/cards, search disclosure/filter, locking errors, trash/read-only encrypted view. Verify EN/VI, modal/full-page editor, back navigation, BFCache, keyboard/screen readers, mobile/background/idle behavior, password-manager round trips, and two-tab lock scope. Run section 9 formative usability checks, required ui-build workflow, and one ui_reviewer after visual design settles.
5. Release gate: network/storage/SSR/analytics sentinel audit proving encrypted title/body/secrets never cross the boundary, except the explicitly authorized conversion back to ordinary. Update public privacy copy in EN/VI to distinguish opt-in E2EE from ordinary plaintext application storage, disclose metadata/old-copy limitations, and remove unsupported automatic server-encryption claims. Run appropriate note/sync/search/recovery/account regression suites, `pnpm lint`, production build (with required elevated build permission), and browser coverage. Independent security review before a beta accepts real user notes.

Rollout: deploy additive schema and server read/write protections first, then updated storage/client behavior, then enable a small beta only after all gates. Flags may stop new encryption setup/conversion but must preserve unlock, encrypted read/save, recovery, and deletion for existing encrypted notes. Never roll back to a plaintext-only server/client once ciphertext exists; fixes roll forward. No automatic decrypt migration, no destructive database rollback.
