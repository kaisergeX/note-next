# All notes and search

## 1. Paginate All notes

Use TanStack Query to fetch owner-scoped cursor pages in the existing newest-first order, with note ID breaking ties on creation time. Fetch bounded card previews on the list and the full document when opened. Fetch the next page near the end of the list and provide an accessible load-more action with retry.

Verify page boundaries with identical timestamps and failed requests. A browser draft can belong to a saved note on a later page. Resolve its identity independently of which pages are loaded so the draft opens the correct editor, contributes to the review filter, and appears once when its page arrives.

## 2. Render long masonry lists

Use native CSS masonry wherever supported. Align the stylesheet and the feature check with the supported syntax, including `display: grid-lanes`. Replace or adapt the existing masonry hook as needed. Use TanStack Virtual's measured lanes as the JavaScript fallback.

Prototype native windowing with measured page spacers. Compare against continuous native masonry on a long list before adopting page-level windowing, since a tall final card in one page can leave gaps above the next. Verify mounted card count, keyboard focus across page boundaries, resizing, and scroll restoration after closing a desktop dialog or returning from the mobile editor.

### Phase 2 implementation and measurements

The collection prefers `display: grid-lanes`, then the older `grid-template-rows: masonry` syntax, with matching stylesheet and feature checks. Unsupported browsers use TanStack Virtual measured lanes. Source order stays unchanged; focused cards, their immediate neighbours, and the editor return target stay mounted. Collections of up to 72 cards retain ordinary rendering and list transitions. Larger collections mount card bodies near the viewport. Collection scroll corrections use immediate scrolling because the application's smooth scrolling otherwise competes with measurement updates.

Native page spacers were rejected after a real WebKit comparison: 240 cards in three lanes, with a 700px final card per 24-card page and 100px other cards, occupied 11,664px in continuous masonry and 15,120px in separate page grids. Page boundaries added 3,456px overall; the first next-page card started 584px later. Individual measured shells preserved continuous native positions with 0px drift in that prototype. The implementation therefore retains native per-card shells and windows their contents rather than separating network pages into grids. Shells have cached or estimated heights and are hidden from accessibility APIs while empty. Native shell/observer count remains proportional to loaded notes; expensive card contents are bounded by the viewport. TanStack retains layout metadata for all loaded items while bounding mounted cards.

Installed browser probes on 2026-11-08: Chromium 158.0.8127.18 and Firefox 159.0 supported neither native syntax; Playwright WebKit 27.2 supported `grid-lanes`. At 240, 480, and 960 loaded notes, top-of-list mounted card-body counts were respectively 16/16/16 in Chromium and 12/12/12 in native WebKit (an earlier run measured 20/20/20) at the desktop test viewport. A mixed-length 480-note Chromium collection had 38 mounted cards, 20 visible cards, and no overlapping cards in a deep-scroll sample. Native Windows WebKit exercises the native implementation, but does not establish physical Safari/iOS momentum-scroll or device behavior. Its default sequential-focus policy skipped hyperlinks even with Alt-Tab; native tests verify source-order button traversal across network-page boundaries and programmatic link focus/return. Full keyboard link traversal in Safari remains a device/browser-preference check. Chromium and Firefox tests traverse links and buttons with ordinary Tab. Offscreen native shell heights are estimates until measured; measurements and editor-return layout caches live only within the signed-in collection provider.

The reproducible native comparison is `node scripts/masonry-prototype.mjs` (requires installed Playwright engines). Targeted browser regressions live in `scripts/browser/note-masonry.spec.ts`, alongside the pagination, browser-work, and transition suites. They use disposable local accounts/databases; no normal app database is migrated or seeded for phase 2 verification.

## 3. Search the collection

Search titles for all active notes owned by the user, plus visible body text for unencrypted notes. Titles remain plaintext. Encrypted bodies are searchable by title only in this plan. A complete on-device body index would require downloading and decrypting the collection on each new device and protecting any persistent index. Revisit that cost if title search proves insufficient.

Search across unloaded pages and reconcile results with browser drafts using the same version shown on the card. Benchmark PostgreSQL trigram indexing on representative long notes. Test mixed scripts, text without spaces, short queries, symbols, and words split by inline formatting. When a body becomes encrypted, remove derived plaintext search data and snippets. Reconcile the public privacy description with the intended encryption behavior before shipping search.

### Phase 3 implementation and rollout

Search uses case-insensitive literal substrings with Unicode NFC equivalence and normalized whitespace. Accents and symbols remain meaningful. Inline formatting preserves adjacent text; blocks and line breaks separate text. There is no language tokenizer, fuzzy matching, or minimum query length. Queries travel in authenticated POST bodies. Results are owner-scoped, exclude Trash, and use creation time plus note ID cursors with PostgreSQL microseconds. Each page contains at most 24 display results and bounded plain-text snippets; it is never an editor baseline.

`note_search_documents` stores canonical visible text separately from note HTML. Note writes and projection updates commit together. Source-change triggers invalidate stale documents; encryption transitions and projection-write guards clear derived body text. Encrypted search hits and ordinary list/identity previews return no body content. Backfilling does not modify note revisions or editor content. Theme edits and idempotent acknowledgements reuse an existing projection instead of parsing or indexing the body again.

Browser reconciliation evaluates the exact displayed version. A single draft can add a match or suppress an older server hit; ambiguous hidden versions do not become search results. Saved acknowledgements remain temporary overlays until a newer successful authoritative query reconciles them, including when the note is absent. Extracted draft/saved text is memoized between query renders. Counts describe loaded reconciled matches until pagination is exhausted. Query and review-filter state remain in the signed-in collection provider for dialog/mobile return; search terms are not added to note URLs or persisted as a local index.

The search field stays disabled through server hydration so early input cannot be lost. Return markers survive navigation into the editor before they can be consumed on return. On measured-lane resize, the virtualizer aligns the selected item after measurement resets; native masonry retains physical anchor correction.

Apply this sequence to the intended deployment database; do not reuse the normal app database for QA:

1. Verify `DATABASE_URL` and `POSTGRES_URL_NON_POOLING` identify the same intended database, then apply checked-in migrations (`pnpm db:migrate` locally, or `pnpm db:prod:migrate` for the production environment). The migration requires permission to enable `pg_trgm`.
2. Deploy the writer code that maintains projections. Existing notes initially have no document. During preparation the search API returns `503` with `code: search_not_ready`; the UI offers retry and Clear, rather than reporting false no-results. Ordinary notes remain available.
3. Run the resumable backfill against that same database. For local configuration: `node --env-file=.env.local --conditions=react-server --import tsx scripts/backfill-note-search.ts`. For production configuration, use the corresponding explicit environment file. Batches lock at most 50 notes, fill only missing documents, and serialize with writes. Restart after interruption; the final assertion must report zero missing documents before search is treated as ready. Direct SQL imports/source edits invalidate projections and require this backfill again.
4. Verify a known older note matches independently of loaded list pages, plus a title-only encrypted fixture whose body never appears in results. The public privacy claim below remains unresolved and requires the owner's release decision.

The [recorded benchmark](../scripts/note-search-benchmark-results.json) uses 12,000 synthetic notes across four owners, 124.4 MiB source HTML, and 626 long notes on PostgreSQL 15. Selective trigram queries improve substantially; common words can remain slower. Patterns without extractable word trigrams use explicit owner-only primary-key scans: common short/symbol queries were about 3–4 ms, absent ones about 50 ms for 3,000 owned notes. The search table including indexes/TOAST occupied about 278 MiB versus 89 MiB for notes; the body GIN alone was about 105 MiB. These local warm-cache measurements and small sample percentiles are not production latency guarantees. The report separately records real body-edit, theme-only, idempotent-save, repository-call, and response-size costs.

Privacy audit: `app/[locale]/trust/privacy/page.tsx` claims automatic title/body encryption “on our server” at the two encryption passages. The verified application path persists title/content directly as text, defaults `isEncrypted` to false, exposes no note encryption editor control, and contains no note encryption/decryption transform. The flag is a search exclusion boundary, not an encryption implementation. Infrastructure/storage/transport encryption settings were not established by this code audit. No policy text or encryption system was changed. Clearing a projection does not promise erasure of historical WAL, backups, or old MVCC versions; reconcile public copy before shipping.

Backend regressions run with `node --env-file=.env.local scripts/run-note-search-tests.mjs`, which creates, migrates, and drops only its own disposable loopback database. Client reconciliation tests run with `node --import tsx --test scripts/note-search-client.test.ts`. Browser search regressions live in `scripts/browser/note-search.spec.ts` and require the app and runner to share a dedicated loopback database whose name contains `_test`; see the existing editor testing guide for fixture sign-in and server-origin setup.

Verified on 2026-11-08: 41 database/account/note regressions and eight client reconciliation/request tests passed. Chromium passed 11 search cases plus the 10 existing pagination/masonry cases; installed WebKit passed 11 search cases plus three native masonry cases. Coverage includes unloaded notes, inline/NFC/symbol queries, loaded/exact counts, clear/Escape, retry/preparation failures, account switching, stale-draft suppression, review filtering, encrypted body exclusion, acknowledgement expiry after external edits, modal/mobile focus return, resize, and bounded card contents through 960 loaded notes. The documented backfill command prepared legacy disposable fixtures, verified zero missing documents, and a rerun prepared zero rows. `pnpm lint`, `pnpm build`, formatting and migration consistency checks passed.

The UI reviewer returned PASS at 1440px Paper & Ink light and 390px Bookish dark, including Vietnamese controls, retry/return, overflow, targets and contrast. Local Vercel telemetry returned 404 outside the reviewed feature. These checks do not establish physical iOS/Safari momentum behavior, physical IME operation, every appearance/browser combination, or deployment infrastructure encryption. All migrations and QA fixtures used disposable databases; the normal database and public privacy page were not changed.
